# 在 Codex 中验证 ShuTong

先按 [源码安装说明](release-0.1.0.md) 完成构建与安装，再新建任务，让 Codex 加载 Skill 和工具。已有任务可能仍持有旧工具列表。当前版本先检查短主干，超出预算时最多修订一次。

## 先体验主干与详情

在新任务中提出一个含多个方面的问题，例如：

> 为一个20人团队设计内部知识库问答的最小方案：已有500份Markdown文档，每周更新，预算有限且文档有不同访问权限。请给出结论、关键步骤、方案之间的关系、风险和实施细节。作为一般设计讨论，不查资料、不读仓库、不修改代码。

预期先看到简短主干，保留结论、关系和关键条件；末尾有“可展开”的话题及“展开细节与知识点”链接。打开本地页面，点击某个详情标题，应看到该部分内容。简单回答不强制提供展开列表；“这次完整详细讲、不要折叠”应直接给出详解。“提供实施细节”可以由展开区满足，不会仅因出现“细节”二字就取消分层。

这是独立页面里的折叠，尚未提供 Codex 消息内的原生折叠控件。页面支持回答、知识点、设置三个视图。你无需每次点开任何面板，正常提问即可。

## 查看记录与调整行为

点击“知识点”可查看本轮解释的内容及次数，默认阈值 1。隐藏的详情不会因提前生成而计数；展开后才会计入对应解释，反复展开同一回答不加次。若详情里没有新的概念解释，展开也不应凭空加记录。

“设置”可单独关闭自动计数、根据记录调整回答、主干与细节展开等能力。也可直接在对话中说“只在这个任务里关闭主干与细节展开”或“这次详细讲，不改长期设置”。总开关关闭后，新回合不自动注入策略；需要恢复时明确让 Codex 打开 ShuTong 面板并重新启用。

知识点勾选、最近记录撤销、导出等均为可选管理，不是日常操作要求。取消某知识点勾选会清零其当前次数；仅仅追问不会清零，不需要额外设置“仍需解释”。

## 区分流程验证与实际增益

同一任务里第二次不解释 RAG，不足以证明工具有效：原生模型本来就可能避免重复。检查 ShuTong 记录只能证明流程；要判断收益，应使用相同模型、相同问题、新任务和隔离的启用/关闭数据，检查关键信息和总工具成本。

2026-09-26 的一个实际对照里，启用后首层正文 514 字符，关闭为 2323；但输出 Token 为 3715 对 1880。它证明了该样例的分层呈现，不能证明普遍收益，更不能证明节省 Token。

## 数据和范围

按本机系统用户的 Codex 配置启用，跨项目、跨任务共享本地知识档案；同一配置的 CLI 也适用，不跨电脑同步。可选领域、任务和本轮覆盖不改变默认全局范围。

识别知识点、判断是否需要解释及提炼关键条件仍依赖模型，可能漏记或粒度不一致。计数持久化、去重和证据片段检查由代码执行；并不判断用户真实掌握程度。同一 turn 的重放有去重；宿主某些重新生成操作若创建新 turn，可能被记成新一次。

详情默认暂存 24 小时，过期拒绝访问并在后续新回合清理；需要提前清除可在面板操作。[完整行为说明](progressive-output.md)、[设置说明](settings.md)。

## 如果没有加载

用 `codex plugin list` 确认实际安装身份；仓库安装是 `shutong@shutong-preview`，个人开发安装可能是 `shutong@personal`，不要同时安装两份。若宿主提示钩子待审核，通过其钩子管理界面检查 UserPromptSubmit、Stop、Interrupt 三条钩子。定义变化后可能需要重新信任。不要关闭沙箱或全局审批来使用 ShuTong。

旧面板会在新版本调用时被替换；旧链接因此可能失效，重新让 Codex 打开面板即可。没有面板时直接追问相应细节，仍可继续对话。

## 开发更新

```sh
pnpm install --frozen-lockfile --ignore-scripts
pnpm check
pnpm build:plugin
```

复制构建后的 `plugins/shutong/` 到个人市场已登记的来源目录，执行 `node scripts/configure-local-plugin.mjs /absolute/path/to/shutong`，按插件开发更新流程更新缓存标识并重新安装。本机来源为 `~/plugins/shutong/`。不直接修改安装缓存。

其他安装路径及兼容边界见 [安装方式](installation-options.md)。

## 历史：主干检查阶段验收结果

主干检查版已通过 69 项回归。两个设计问题各两次的真实样本，首层正文平均缩短约 37%；输入/输出 Token 平均约增加 19%/33%，属于阅读稳定性与生成成本的取舍。关键风险识别仍依赖模型，不能把字数合格当作内容必然完整。

## 跨任务记录命中

新任务可能把同一概念换成另一个 ID。新版会返回有限名称候选，模型确认同一概念后选用旧 ID；不需要用户每轮整理名称。只凭同名不自动合并，范围不同的组合概念也不应被直接当成已知。

本次实测修复了这一命中问题，但空档案对照本来也较少重复基础定义，尚无额外阅读或 Token 收益证明。验证时应查看真正的输出内容，不能只看计数增长或 suppress-basics 标签。


## 常见安装问题

- `codex plugin` 不存在：宿主版本不支持当前安装入口，需要兼容的 Codex，或暂用独立 Skill；第二宿主自动计数待实现。
- Node 提示 SQLite 为实验性模块：这是当前 node:sqlite 的提示，本身不代表失败，应查看实际错误及退出状态。
- MCP 启动失败：确认已构建，且源码目录没有移动；在仓库根目录重新执行 configure-local-plugin，再安装。
- `pnpm check` 无法监听端口：集成测试需要临时回环 HTTP 服务，不需要关闭宿主全局审批。
- pnpm 提示 store 不匹配：沿用原 `--store-dir`，或在干净检出中重新安装，不必改全局配置。
- `pnpm probe:codex` 仅检查协议；`--installed` 当前硬编码检查 personal 开发身份，不能据此判断 preview 安装失败。
