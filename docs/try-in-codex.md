# 在 Codex 中验证 ShuTong

当前版本是本地可验证版本：Skill、MCP 工具、回答前后钩子和知识点面板已经接通。默认阈值为 1，记录存于本机。

## 本机开始使用

本次开发已将 `shutong@personal` 安装到个人插件目录，并通过 Codex 正常钩子界面启用了 ShuTong 的 UserPromptSubmit、Stop、Interrupt。没有关闭沙箱或绕过钩子信任检查。

请在 Codex App 中打开一个新任务，让它加载新插件。无需每轮启用技能、点击面板或手动提交记录。

依次发送：

1. “请简短解释什么是 RAG，给一个使用场景。”
2. “我准备用 RAG 做公司知识库问答，实施时要注意什么？”
3. “请从头再解释一下 RAG 是什么，不要省略基础定义。”

预期：第一次回答包含定义，回答结束后知识点计数至少为 1；第二次默认省略重复定义，保留新的建议和限制；第三次正常重新解释。若第二次又解释了一个新的子知识点，它仍可能新增记录或增加相关计数，不是固定每轮输出同一长度。

回答末尾的“本次知识点”链接会打开本地面板。可以查看次数、勾选已掌握，或展开详细设置修改阈值。不打开面板，自动记录照常运行。

也可以直接对 Codex 说：“打开 ShuTong 知识点面板。”

## 如何确认是否真的生效

- 模型工具记录中出现 ShuTong `context` 和 `stage` 调用。
- 面板显示“已核对本轮回答”，并显示对应知识点及解释次数。
- `stage` 仅准备元数据，不增加次数；Stop 核对最终回答中的解释片段后才计数。
- 如果显示“本轮未提交知识点”，或者没有工具调用，不能只凭回答变短就判定生效。
- 如果需要重复进行同一个概念的首次验证，可以在面板主动取消该知识点的勾选，重新累计。

默认正式档案没有混入开发用的哈希表验收记录。开发验证使用独立临时目录。

## 界面与能力边界

当前提供回答末尾链接和本地独立面板，尚不是聊天气泡内部的原生折叠组件。面板只监听 `127.0.0.1`，使用随机访问令牌；关闭页面后空闲 30 分钟退出。链接失效时让 Codex 重新打开面板即可。

知识点识别和解释片段提取由当前回答模型完成，可能漏记或采用不同粒度。运行时只验证提交的片段是否真的出现在最终回答中，不声称能判断用户真实掌握程度。没有额外调用一个模型来分析完整对话。

主干优先、显式追问优先和关键条件保留依赖模型遵循输出策略；计数持久化、去重和片段存在检查由代码执行。

当前按 Codex 的会话与 turn 标识去重。同一 turn 的重放已验证；UI 中某些“重新生成”如果创建了新 turn，可能被记成新一次，尚未验证所有客户端路径。

## 如果没有加载

先确认在新任务中启用了 `shutong@personal`。如 Codex 报钩子待审核，在其 `/hooks` 管理界面检查 ShuTong 的三条钩子；定义变化后可能需要重新信任。安装或升级时的一次性检查不应变成每轮操作。[官方钩子说明](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)

已有任务可能保留旧的工具列表；开始一个新任务是最简单的验证边界。不要为了使用 ShuTong 关闭沙箱或全局审批机制。

## 开发与重新打包

```sh
pnpm install --frozen-lockfile --ignore-scripts
pnpm check
pnpm build:plugin
```

插件位于 `plugins/shutong/`，包含已打包运行时，不要求安装端再解析 workspace 依赖。复制到本地插件来源目录后，运行：

```sh
node scripts/configure-local-plugin.mjs /absolute/path/to/shutong
```

这个步骤写入当前机器的 Node 和 MCP 绝对路径。当前 Codex 版本支持钩子里的 `PLUGIN_ROOT`，但实际验证发现它不会展开 MCP argv 中的同名变量。

本机个人市场来源为 `~/plugins/shutong/`；安装使用 `codex plugin add shutong@personal`。开发更新需要更新版本缓存标识并重新安装，不直接修改 Codex 缓存目录。
